# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Read SPEC.md before touching anything - it is the design of record and short.
- This repo's own check command is `script/check` (required-tools preflight, gofmt, vet, build, test, then inspector-gate's and fabrica-contract-check's own shell tests), wired up via `.inspector.json` - inspector dogfoods itself. Tests run under `-race`, which needs cgo and a C compiler locally (CI's ubuntu-latest already has one) and costs about a second of suite time; keep it, the code captures subprocess output concurrently. `-race` is unsupported on some platforms (32-bit x86, linux/arm, freebsd/arm) - use `CGO_ENABLED=0 go test ./...` there instead of `script/check`. Also needs Docker for `internal/container`'s own tests, most of `internal/inspector`'s, and the end-to-end ones in `cmd/inspector` - they skip cleanly (`requireDocker` in each package's tests) rather than fail when no usable runtime is present, the same tolerance `TestLoadConfig_UnreadableFile` already extends to a root-run suite.
- Two similarly-named paths, different jobs: `.inspector.json` (tracked, project config - the check command, the container's resource limits, and `protectedPaths`) vs `.inspector/` (gitignored, one JSON report per local run plus the last failed image build's log, notes only, never authority). The image the check runs in is not in either: it is the project's own tracked `Dockerfile.inspector` at the repo root.
- `internal/inspector.Run` refuses on a dirty working tree, because a result is only honest when it's bound to a commit that actually matches what's on disk. `WorkingTreeStatus` excludes untracked files in `.inspector/`, but not tracked changes there, and rejects assume-unchanged or skip-worktree index flags that could hide modified tracked content. Without the narrow report exclusion, a repo that never gitignores `.inspector/` would go permanently dirty after its first report. Don't broaden or drop it. The publication recheck compares only the post-check snapshot, so it never proved source immutability and must not be described as doing so - issue #27 is what does that, by mounting tracked source read-only (`container.ResolveWorkspace`, `notes/20261023-source-read-only-during-checks.md`), and the recheck is deliberately kept beside it, unchanged, for the different job of binding a result to one exact commit.
- Exit codes are a deliberate split, not pass/fail: `0`/`1`/`2` are reserved for verdict attempts, and anything that is not a verdict attempt at all gets `64`. The list itself is owned by README's Use section and the const block in `cmd/inspector/main.go` - read it there, don't restate it. The invariant every caller that shells out to inspector depends on: never treat `2` as red, and never confuse `64` with a verdict attempt. (inspector-gate is not one of those callers - it reads the commit status, never an exit code.)
- This is issue #1 of the roadmap in `gh issue list` (or `gh-axi issue list` under firstmate) - the installer (#5) remains open. The fixer (#2) is closed and superseded by fabrica#95: Inspector never edits a judged project. Issue #13 (run the check command in a container) is built, in `internal/container`, and the gate workflow (#4) is built too - both are described below. Issue #43 (resource limits and a non-root user for the check container) is built, and so is issue #47, its deferred fourth part: the check image is built from the project's own committed `Dockerfile.inspector`, a project without one is refused by that name, and the container is network-denied with no opt-in left - see `notes/20261025-project-image-from-committed-dockerfile.md`.
- A green local run (issues #3 and #18) has to complete the publication sequence in `cmd/inspector/main.go` before the CLI can exit `0`: stage the checked commit on `origin`, post its GitHub status, then update the explicitly caller-named pull request branch. `--branch` is required, is never inferred from checkout state, and may not name the remote default branch. HEAD, the working tree, and the pre-check publication target are revalidated after the check and before any remote operation; the push URL determines the status repository and may not contain embedded HTTP credentials. Pushes use a temporary bare repository so checked code cannot supply hooks or local Git configuration, omit `GITHUB_TOKEN` from Git's environment, are bounded and non-interactive, and kill their complete process group on timeout; platforms where that guarantee is unavailable still run checks and return local red, but do not start green publication. The status context is the stable string `inspector`, which `inspector-gate` (#4) keys on; the token comes from `GITHUB_TOKEN`. Later failures deliberately leave partial state rather than compensate and report remote state as unknown when a response may have been lost; a written status request with no response is reported as "stamp sent, outcome unconfirmed." Incomplete publication exits `2`, distinct from a refusal, which never attempts to push or publish. v1's red policy is no publication at all and exit `1`.
- The examiner (`inspector examine`, implemented in `internal/examiner`) is intentionally unlike the project check: its sealed container receives request text, a feature map, an always-true list, names-only changed files, and pre-task changed tests plus an app URL - never a repository mount, implementation diff, or worker-written file content. Do not add one. `runtime/Dockerfile` locally builds its trusted pinned runtime; examination never builds or pulls it. The model proposes scenarios and assessments, while the per-capability record derives every verdict. A found bug posts `failure`; an otherwise incomplete examination posts `error`; both facts remain in the verdict. See `internal/examiner/README.md` and README's Examiner section.
- Before building anything about containers, mounts, or runtime, read Fabrica's `src/containment/` and `src/brain/adapters/docker/Dockerfile`. They are the authoritative prior work for Inspector's containment decisions.
- Any deviation from an owner ruling must be stated under its own heading in the pull request description. Do not leave it for review to discover.
- The check command runs inside a container (`internal/container`, driven by `check.go`), not on the host: at `container.WorkspaceDir`, where `container.ResolveWorkspace` (issue #27) gives it a throwaway writable directory with the repo root's tracked top-level entries and `.git` mounted over it **read-only** - one mount each, so the commit under check cannot be modified, while `mkdir dist` in the repo root still works - plus whatever untracked, gitignored entries it already had, still writable, plus - read-only, and only for a linked worktree - whatever `container.ResolveGitMounts` resolves (see the next bullet), network-denied. `notes/20261023-source-read-only-during-checks.md` owns why that layout and not an overlay, and the two residuals (a root symlink is carried as a link and so is replaceable; files the check adds to its own tree land in the discarded workspace where the publication recheck no longer sees them). `CheckResult.Workspace` belongs to the caller, which discards it after the report is written. The network denial is now unconditional and the image it runs is built, not named: `internal/inspector.BuildProjectImage` builds the project's own committed `Dockerfile.inspector` (fixed path, no config key) and tags it by that file's hash plus its bases' resolved image IDs, and the retired `image` and `network` config keys are refused by name rather than ignored - issue #47, owned by `notes/20261025-project-image-from-committed-dockerfile.md`, which also holds the one case where the ruled tag cannot see a change and what is done about it. The same issue bounds the container's memory, CPU, and process count (`container.Limits`, defaulting to Fabrica's own worker numbers - 2g/2/512 - and overridable per project in `.inspector.json`) and runs it as `container.ResolveUser`'s resolved host uid:gid rather than the image's default, so a runaway or hostile check owns nothing on the host it didn't already own; a rootless Docker daemon is detected and left as root (which, from outside its own user namespace, already is the unprivileged host account). `container.EnsureAvailable` refuses loudly, before ever attempting a run, when Docker is missing or its daemon is unreachable - never fall back to running the check command on the host, that's the one thing this exists to prevent. `RunCheck` (`check.go`) distinguishes docker itself failing to start the container (an infrastructure failure, surfaced as a Go error - `container.Cmd.Started` reads back the `--cidfile` Docker writes at container creation, before the command inside it ever runs) from the check command's own exit, signal, or timeout (a normal `CheckResult`, unchanged shape). Killing the container on timeout (`docker kill`, not a local process-group kill - that older mechanism died with the direct `sh` execution it protected) rides the kernel's own guarantee that killing a PID namespace's init process takes every process it forked down with it - stronger than the `Setpgid` group-kill it replaced, and the reason `TestRunCheck_TimeoutKillsChildProcesses` still passes. Whether that kill actually worked is read from `container.Cmd.KillError`, never inferred from what `Run` returned - `exec.Cmd.Wait` drops `Cancel`'s error whenever the `docker run` client itself exited badly, which is precisely the case where the container is still running - and a refused kill stays a `TimedOut` verdict with docker's own message on stderr and in `Output`, never an infrastructure error that would cost the run its report. It also sets `CheckResult.KillFailed`, which is reporting only (nothing classifies on it) and exists so `run.go`'s refusal never tells someone the check was killed when docker says it wasn't.
- Git works inside the container only because `container.ResolveGitMounts` (`internal/container/git.go`, issue #31) puts it there, and only for a linked worktree - every worker in the factory works in one. Such a worktree's `.git` is a pointer file naming the project's shared git directory by absolute host path, outside the mount, so the mount is that directory, read-only, **at exactly the path the pointer names** (git records the physical path, so the mount source and target are both `filepath.EvalSymlinks`'d - macOS's `/var` -> `/private/var` is the trap). Over its `config` goes a shadow-mounted throwaway copy carrying only `[core]` plus allowlisted `[extensions]` keys: that file is the one thing in a git directory that can carry a credential, and the check command is arbitrary project code. Dropping `config` entirely does not work (`fatal: not a git repository: (null)`); a `[core]`-only one does. An allowlist, never a denylist - a denylist fails open on the first unanticipated form (`[remote.origin]`'s dotted spelling, `http.<url>.extraheader`, `url.<base>.insteadOf`, `[credential]`, `[include]`), and anything it cannot vouch for is refused by name (wrapping `ErrGitDirUnavailable`, which `run.go` turns into a refusal and exit `2`), never dropped or guessed. This is a port of Fabrica's `src/line/worktree-git.ts` plus its two READMEs; read those before changing it, including why a per-run copy of the object database was built and rejected. Three tests own the result and must not be weakened to pass: `TestContainerCannotReadHostGitConfig`, `TestContainerCannotCommit`, `TestLinkedWorktreeGitIsReachable`. The container also carries one `GIT_CONFIG_KEY_n=safe.directory` / `GIT_CONFIG_VALUE_n` pair per path New mounts (`WorkspaceDir` plus each `ReadOnlyMounts` target, counted in `GIT_CONFIG_COUNT`) rather than git's own wildcard `*` - issue #43 gave inspector the same `--user <host-uid>:<host-gid>` Fabrica's worker always ran with (`container.ResolveUser`), so a bind-mounted repo's host ownership now normally matches the uid running inside, and the scoped list is defense in depth for whatever case still doesn't (a rootless or remapped daemon, a filesystem-sharing backend that doesn't preserve uids) rather than a blanket trust of any directory. This has to be environment, not a config file - git honors `safe.directory` only from protected configuration.
- A container's own init process (PID 1) is immune to a signal sent to it from *within* its own PID namespace, even `SIGKILL` - real Linux kernel behavior (`pid_namespaces(7)`), not a bug. A check command's `kill -9 $$` is therefore a no-op when that check command is the container's top-level process; a signal delivered from outside the namespace (`docker kill`, the OOM killer) still works normally. Tests that need a real signal-killed check command fork a child to kill instead (`sh -c 'kill -9 $$' && true`, matching README's own `npm test && npm run lint` shape) - see `TestRunCheck_CompoundCommandSurvivingKilledChild`.
- Inspector's own `Dockerfile.inspector` builds on `cimg/go:1.22`, because `script/check` needs more than a Go toolchain: gcc and CGO_ENABLED=1 for `-race`, plus the shell tools `.github/scripts/required-tools.sh`'s `REQUIRED_TOOLS` names, for `.github/scripts/inspector-gate_test.sh` - `jq` among them being a real runtime dependency of the shipped gate script, not just its tests. `golang:1.22` was the earlier choice and carries no `jq`, so the gate tests failed inside the container while passing on CI's host. `required-tools.sh` is the single source of truth for that list - `script/check`'s preflight and `inspector-gate_test.sh`'s own drift test (which re-runs itself with PATH restricted to exactly that list, catching a tool the list forgot rather than a reviewer having to notice) both read it, so it can't drift between the two the way the hand-duplicated version did the first time (`tr` was missing). The one thing that drift test cannot prove is its own scaffolding - `mktemp`, `ln`, `sed` and `rm` run in the outer, unrestricted-PATH copy, so they are listed outright instead of being verified. The container is network-denied with no opt-in, so nothing can be installed at check time at all - any replacement base has to carry the whole list already, or install it in `Dockerfile.inspector`, where the build still has the network.
- `.github/workflows/inspector-gate.yml` (issue #4) runs on `pull_request_target` with no `actions/checkout` at all, ever (SPEC.md section 8) - so it can't run `.github/scripts/inspector-gate.sh` as a file on disk. Instead it fetches that script's own content from the BASE BRANCH TIP (`base.ref`, not the payload's `base.sha`) via the Contents API and `source`s it, the same trust boundary and same ref used for reading `.inspector.json`; the tip is deliberate, so a tightened `protectedPaths` applies to already-open pull requests and the script comes from where GitHub loads the workflow file from. Never add a checkout. An `on: status` trigger was tried and REMOVED: a status-triggered run's check attaches to the default branch's tip, never the pull request's head, and a status event cannot be filtered by context. Do not reintroduce it: inspector#18 now stages and records green work before it updates the pull request branch, so the ordinary `synchronize` run has the status from its first look. The gate only reads statuses, so `statuses: read` is sufficient and `statuses: write` is intentionally absent.
- inspector-gate's protected-path list is `.github/**` and `.inspector.json` (hardcoded in the script, `ALWAYS_PROTECTED`), plus the base branch's `.inspector.json` `protectedPaths` entries - nothing else. A project's own check command is deliberately NOT derived from its `check` field: that was tried (auto-protect when `check` reads as a bare path) and reverted after landing three review findings in the same spot, because telling a path from a command line by looking at the string never holds up in general - don't reintroduce it. This repo's own `.inspector.json` lists `script/check` under `protectedPaths` explicitly for exactly that reason. Every uncertainty in reading `.inspector.json` fails CLOSED except a genuine 404; don't relax that, a gate protecting less than it claims is worse than one that refuses. The script's pure decision functions are unit tested by `inspector-gate_test.sh`, wired into `script/check`; the GitHub API orchestration in `main()` is not testable outside Actions and is documented as such rather than mocked.

- `cmd/inspector/testdata/fabrica-consumer-contract.json` (the fixture `TestFabricaConsumerContract` checks inspector's real behavior against) is a copy of Fabrica's own `src/inspector/consumer-contract.json`, not an independent fact - issue #109. `.github/workflows/ci.yml`'s `fabrica-contract` job and `.github/scripts/fabrica-contract-check.sh` are the Inspector-side half: every pull request and push to the default branch fetches Fabrica's file from Fabrica's default branch (`inactdev/fabrica`, resolved live, the same Contents API read `inspector-gate.sh` uses for `.inspector.json`) and fails, printing the diff, if the two no longer match byte-for-byte - so the only way the local copy is meant to change is a Fabrica-made pull request replacing it wholesale. Unlike that `.inspector.json` read, a 404 here is never a safe absence: there is no state where Fabrica's file is missing and inspector's copy can still be trusted, so every non-200 response fails closed and is named, 404 included. The script's pure function (`decode_contents_response`) is unit tested by `fabrica-contract-check_test.sh`, wired into `script/check`, the same split `inspector-gate.sh`/`inspector-gate_test.sh` uses. The matching Fabrica-side job (opens a pull request here when Fabrica's copy changes) is Fabrica's own task, not this repo's.
- `internal/llm` is the vendor seam (issue #42): one `Adapter` interface ("ask a model with these tools") with an `AnthropicAdapter` and an OpenAI-compatible `OpenAIAdapter`, so no caller is written against one vendor's request shape. The examiner (`internal/examiner/agent.go`) was the first caller; the code reviewer (issue #34, `internal/reviewer`) is the second, sharing it rather than growing its own vendor code. Unlike the examiner, the reviewer runs with no container and no repository mount: its whole input is a caller-supplied unified diff (`--diff`), annotated with explicit new-file line numbers before it ever reaches the model, so a finding's file:line pointer never depends on the model's own diff arithmetic, and a finding naming a file outside that diff is rejected rather than recorded. It reports only - no commit status, no gate - because SPEC.md's reviewer is read-only and non-blocking by design. Vendor selection is one fixed rule with no per-vendor table, in `internal/llm.EnvVarNames`/`Resolve`: uppercase the vendor name and append `_API_KEY`, and for every vendor except `anthropic` also `_BASE_URL` - secrets are read by name from the environment and never accepted on a command line or passed as `=value` to `docker --env` (`internal/examiner/container.go` forwards only the name, same mechanism as `AnthropicAPIKeyEnvVar` already used). `--vendor` on `inspector examine` defaults to `anthropic` when omitted, and that default is recorded explicitly - `vendor: anthropic (default, no flag given)` - in both the JSON report and the posted `examiner` status (`examiner.Result.Vendor`, set centrally in `cmd/inspector/examiner.go`'s `finishExaminer`), per the ruling that the vendor choice must never be silent.
